# WEB SDK examples v2

## Streaming examples

Serve the SDK distribution over HTTP or HTTPS with `flashphoner.js` at its root.
The original examples remain available under `examples/demo`.

| Example | Page under `examples/v2/streaming` | Controls |
|---|---|---|
| Streamer | `streamer/streamer.html` | Start publishes the camera and plays a server preview; Stop ends both streams. |
| Player | `player/player.html` | Start/Stop, volume, unmute, fullscreen and provider-specific playback. |
| Two Way Streaming | `two_way_streaming/two_way_streaming.html` | Connect, independent publish/play, JSON data and availability checks. |
| Firewall Streaming | `firewall-traversal-streaming/firewall-traversal-streaming.html` | Two-way streaming with TURN settings and optional forced relay. |
| Screen Sharing | `screen-sharing/screen-sharing.html` | Connect, capture size/frame rate, optional microphone and server preview. |
| Two Players | `2players/2players.html` | One connection with two independently controlled players. |

Streamer and Screen Sharing use a combined address such as
`wss://server:8443/stream`. Other examples have separate server and stream-name
fields. Combined addresses decode the stream-name path once: `s 3` and `s%203`
both publish `s 3`, including Unicode names. Escape a literal percent sign as
`%25`; malformed escapes and names containing a decoded `/` are rejected.
Screen capture requires a supported desktop browser; microphone and
capture permissions are requested by the browser.

Player retains the `streamName`, `autoplay`, `resolution` (for example `640x480`),
`mediaProvider` and `mseCutByIFrameOnly` query parameters. As in the original
example, a nonempty `autoplay` parameter enables autoplay. WSPlayer loads
`dependencies/websocket-player/WSReceiver2.js` and `video-worker2.js` from the v2
distribution. These assets are supplied by the SDK build, not generated by the
example tests. Screen Sharing's extension fallback uses the XPI and icon in
`dependencies/screen-sharing/firefox-extension`. The v2 pages do not load
runtime assets from `examples/demo`.

Status and error messages appear near the affected controls. Failed connection
attempts restore the controls for retry. Connection and stream callbacks ignore
events from earlier attempts.

### Embedded server address

An embedding panel can set `window.WCS_SERVER_URL` to the selected WCS signaling
endpoint, such as `wss://wcs.example.com:8443`, before the example's module runs.
All seven Streaming pages, including Media Devices, use this address when filling
their connection field. It must be a WS or WSS origin without credentials, a path,
query parameters or a fragment. Invalid embedded addresses fail initialization.
Directly opened examples continue to use the page hostname and configured ports.
Explicit hostname or port arguments to `getWebsocketUrl` take precedence over
the embedded address.

### Embedded themes

The six Streaming pages and Media Devices declare `data-wcs-theme="light"` on their root `html`
element. They retain the standalone light appearance by default. An embedding
panel can set this attribute to `dark` or `light` to match its current theme;
`dependencies/css/examples.css` supplies the common palette, including fields,
placeholders, buttons, status messages, focus rings and disabled controls.
Embedding styles should leave those controls and their semantic colors intact.
The original `examples/demo` pages do not opt into this theme contract.

## Media Devices

Serve the SDK directory over HTTP or HTTPS with the built `flashphoner.js` at
its root, then open `examples/v2/streaming/media_devices_manager/media_device_manager.html`.

- `media-device-manager.js` contains the Flashphoner session and stream logic.
- `bitrate-chart.js` draws the bitrate comparison using the Canvas API.
- `stream-statistics.js` pairs Local and Player metrics in a single table without summing them.
- `dependencies/css/examples.css` supplies the layout and visual styling shared
  with the other streaming examples. `dependencies/css/streaming.css` adds the
  simpler examples' forms and playback controls.

Statistics show `No data` for an absent measurement and `N/A` for a metric
that does not apply to that side. Local is publishing; Player is playback.
Use each metric's `?` popup for its Local/Player meaning and units.

## Shared modules

Each example keeps its session, publishing, playback and page-specific controls
in the JavaScript file next to its HTML page. Two Way Streaming and Firewall
Streaming can be copied independently; include their referenced helper modules,
styles, port configuration and the SDK distribution assets.

The examples import small utility ES modules from `dependencies/js`:

- `dom.js`: explicit DOM operations using native browser APIs.
- `server-url.js`: shared port configuration, combined streaming addresses, and
  WebSocket, HLS, REST, and admin URLs.
- `media.js`: aspect-ratio-preserving sizing for video and canvas elements.
- `identifiers.js`: short random stream names.
- `tooltips.js`: help popovers for mouse, keyboard, and touch.
- `streaming.js`: SDK initialization, statuses, errors, required fields and
  media resizing for the streaming examples.

## Server ports

Edit `dependencies/ports.js` for nonstandard WCS ports. Load this classic
script before the example's ES module. It uses the same configuration keys
and defaults as the original examples:

| URL helper | HTTP page | HTTPS page |
|---|---|---|
| `getWebsocketUrl()` | `ws`: 8080 | `wss`: 8443 |
| `getHLSUrl()` | `hls.http`: 8082 | `hls.https`: 8445 |
| `getRestUrl()` | `http`: 8081 | `https`: 8444 |
| `getAdminUrl()` | `legacy.http`: 9091 | `legacy.https`: 8888 |

All URL helpers accept `(hostName, hostPort, ports)` overrides. Otherwise
they use the page hostname, protocol, and the `SERVER_PORTS` global.
`getPortsConfig(ports)` returns a new configuration with missing values filled
from the defaults, including nested `hls` and `legacy` values. It does not
modify the supplied configuration or the defaults.

## Regression checks

Install the repository's npm development dependencies, then run these checks
manually from the repository root with Node.js 20 or later:

```sh
npm run test:examples
```

These checks are not part of the Grunt build tasks. Node.js 20 or later is
required only on the machine running the checks, not on the build agents.

These checks use mocked browser objects and the existing Grunt copy task in a
temporary directory to verify that v2 runtime assets ship without `examples/demo`. They cover
Media Devices and all six streaming examples without accessing a camera,
microphone, or WCS. Real-browser media checks remain separate: exercise
publish/play and repeated Stop/Start, both players independently, JSON sendData,
TURN with relay enabled/disabled, screen capture cancellation and its native
Stop control, plus Safari/Firefox autoplay and fullscreen behavior.
